# SQLite 容量与性能验证（2026-10-21）

本机离线基准通过，稳态日志行数和正文容量均符合配置。10 万条详细日志时，统计汇总与同步裁剪已明显影响并发生成请求，应作为下一阶段性能优化的依据。

## 复现与口径

```sh
npm run build
node scripts/benchmark-sqlite.mjs
```

使用真实临时 SQLite、项目现有查询和写入函数、假 SDK；自动启用外网阻断，结束后关闭服务并清理临时数据库。不会读取生产数据库或使用真实模型凭据。需要本机端口权限。基准为手动运行，不加入常规测试套件。

环境：Node v24.19.0，macOS arm64，SQLite 3.53.3。保留策略：7 天、100000 行、268435456 字节；详细档每行 request_detail 为 1024 字节 UTF-8 JSON，response_detail 为 NULL。载荷字节包含模型字段，不等同于数据库文件大小。

各同步操作预热一次后测量 7 次；下表为中位数 / 最大值，单位 ms。写入探针以 BEGIN/ROLLBACK 保持样本固定，包含写入函数及裁剪开销，排除持久提交与 fsync，不能用于推断耐久写入吞吐量。

## HTTP 并发影响

在 10 万条详细日志上，分别测量 5 次空闲生成请求，以及 5 对同时发起的生成请求与管理统计请求。共 16 次 HTTP（含一次完成检查）、10 次假 SDK 生成，外网阻断记录为 0。

| 请求 | 中位数 ms | 最大值 ms |
|---|---:|---:|
| 空闲 Chat | 35.968 | 39.318 |
| 并发统计时的 Chat | 296.900 | 302.866 |
| 与 Chat 并发的管理统计 | 296.099 | 301.921 |

HTTP 完成检查后剩余 100000 行，载荷 103656400 字节，均在上限内。Chat 响应可能先于 finally 中的同步日志写入与裁剪到达；基准在样本结束后等待一次不写日志的 GET /health，再从另一连接检查稳态容量。行数上限是裁剪后的稳态约束，INSERT 与 DELETE 之间可以短暂超限。

## 结论与限制

- 优先减少统计汇总全表工作及其对主事件循环的占用，再评估每次写日志触发裁剪的成本。详细档统计中位耗时约 256 ms，裁剪约 35 ms，并发 Chat 中位延迟约 297 ms。
- 深分页和筛选选项也随容量增长，详细档末页中位约 114 ms；首屏仍低于 1 ms。
- 本轮仅测量，不修改生产查询、索引或数据库架构。管理写接口时限约束异步等待和正文读取，不能打断同步 SQLite 执行或锁等待，也不能撤销已提交写入。
- 结果来自本机暖缓存、小样本和合成数据，不能代表生产吞吐量、冷启动、磁盘耐久提交、锁竞争或 p95。未运行真实付费上游测试。
